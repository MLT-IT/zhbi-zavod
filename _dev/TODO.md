  Надо скрипт для уменьшения тоже сделать динамическим.


* Сделай так, чтобы в слайдере у самого последнего товара всплывашка с кнопками разворачивалась не вправо, а влево.


* На карточке товара для фанеры и плит ОСБ расчеты происходят при загрузке страницы через JS. Наверно, хорошо бы через fenom это сделать? Потому что везде кол-во добавленного в корзину товара сделано на fenom. При загрузке не надо ждать, пока отработает JS, чтобы увидеть правильное количество товара в корзине.


* При загрузке фильтров сейчас я просто добавляю "::after" с прозрачным блоком, чтобы нельзя было выбрать другой фильтр. Но можно написать лучше — подредактировать стандартный JS файл для mSearch2:
```
    beforeLoad: function () {
        $(this.options['wrapper']).addClass(this.options['loading_class']);
        this.results.css('opacity', .5);
        $(this.options.pagination_link).addClass(this.options.active_class);
        this.filters.find('input, select').prop('readonly', true).addClass(this.options.disabled_class);
    },
```
Тогда можно будет при наведении на чекбокс изменить курсор на какой-нибудь другой.
Но стоит ли оно того?


* Скрипт для подсчета количества отзывов и средней оценки (для микроразметки категорий) не учитывает вложенность. Из-за чего эти данные могут считаться неправильно (если вложенность действительно есть).
Пока решили не доделывать этот скрипт, т.к. отзывы теперь могут заполняться еще и у товаров. Это повлияет на скорость загрузки и без того медленных страниц категорий.
  

* На странице товара есть фото товара или даже галерея. К ней применяется плагин `js-image-zoom`. Этот плагин задает width и height. И это видно. Сначала картинка показывается с одной шириной и высотой. А потом, когда скрипты подгрузятся, ширина и высота меняются. Это не очень красиво.


* Скрит для подмены почты можно улучшить. Вместо того, чтобы хардкодить почтовые адреса для каждого контекста, можно просто написать на JS `document.location.host`. Тогда, если появится новый контекст или у какого-либо контекста изменится домен, то подмена почты не сломается.

* В политике конфиденциальности не меняется почта по UTM. Ни по UTM (зависит от сессий), ни через JS (при загрузке страницы).

### Быстродействие 

* Возможно, если на странице каталога сделать поменьше элементов в блоке mse2_mfilter, то данных с сервера будет приходить меньше, и это ускорит ajax. Кажется, в этот блок (div) входят не только чанки с товарами, а что-то еще. 


* Вместо include в некоторых случаях можно использовать insert. Быстрее будет работать. Но вряд ли разница будет ощутимой. А функции отличаются. И просто заменить их глобальной заменой нельзя.


* Возможно, на сайте есть мусор. Хорошо бы написать скрипт, который от первого id до самого последнего по порядку проходит и ищет товары и связи / картинки. Если товара нет, а связи / картинки есть, то удалить их.
Чем меньше записей в БД, тем быстрее в ней осуществляется поиск. И тем меньше она весит. 


* Я не уверен, но, возможно, где-то я вызываю msProducts только для получения id. А происходит выборка всех полей из БД. Это гораздо медленнее, чем выбрать просто id. Надо просмотреть все сниппеты. И если это где-то есть, то подправить — сделать `returnIds=1`.

* Кажется, в msProducts и / или pdoResources можно указывать, какие поля получать. Если указать, то запрос будет работать быстрее. Так можно ускорить сайт. Редко когда нужны прям ВСЕ поля.


* Можно сильно ускорить время ответа от сервера, если все вычисления для товаров (ключ, единицы измерения и т.д.) делать на JS, а не на fenom. Но стоит ли оно того? Может, и так норм? Может, если все сделать на JS, будет еще хуже.


* Добавить lazyload для видео директора, для видео на странице товара, в FAQ. Может, еще где есть iframe с видео.


* Хорошо бы все сниппеты, которые я писал, сделать статичными или файловыми (и написать тогда для них кеширование). Чтобы можно было искать их код через IDE (глобальный поиск), чтобы они были в GIT.
